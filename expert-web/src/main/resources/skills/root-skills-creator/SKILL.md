# Skill 包生成器

## P0 交付门禁（缺一则整包作废）

- **根 `SKILL.md` 必须物理存在**：位于技能包根目录（与 `01-项目总览` 同级），路径为 `{技能根目录}/SKILL.md`。**禁止**仅在某个版本子目录内写文档却省略该根文件。
- **YAML 头必填且非空**：`name` 与 `description` 必须与平台技能包 zip 校验规则一致，否则下游无法入库。
- **收尾必须自证**：宣称完成前执行并粘贴终端输出，例如 `test -f "<技能根>/SKILL.md" && head -n 25 "<技能根>/SKILL.md"`；禁止只说「已生成」而不附命令输出。
- **委派不可省略**：`02-领域认知/{环节}/整体逻辑.md`、同目录下任意 `{子环节}.md`、`03-实体模型/{实体}.md`（不含 `实体模型总览.md`）**不得**由主会话直接 `write` 生成；**必须**先对该环节/实体调用 **`task`**（OpenCode）或平台文档规定的**等价委派工具**，由 subagent 会话写入。以「赶进度、降复杂度、先交核心」为由跳过委派，**等同整包作废**。
- **规模不设豁免**：无论被分析的是整仓还是**单模块**、源码**只有几十个文件**或更少，**一律不得**因「模块小、主会话能读完」而省略 `task`/subagent；环节数与实体数大于零时，委派规则与大型项目**完全相同**。

## 执行铁律（12 条不可违背）

> 全文其他部分都是这 12 条的展开说明。若只能记两件事：**（1）先有合格根 SKILL.md；（2）环节与实体细节唯经 `task` 派发的 subagent 写入，主会话不得代写。**

1. **禁止一次性写完所有环节**：`整体架构.md` 里有多少个环节，就必须为**每个环节独立启动一个子 Agent**。
2. **禁止只读入口层**：读了任何一个入口文件（如 HTTP handler、路由、controller、gateway）后，必须沿着调用链追到核心业务处理层 → 数据持久化或外部调用边界，直到触及存储层或外部系统边界。
3. **禁止使用占位符**：`{类名}`、`{方法名}`、`100-200` 这种估算行号禁止出现在最终文档里，必须来自真实源码。
4. **禁止 3-5 个大阶段流程图**：处理流程必须拆解到 `类.方法` 级别，必须有分支和异常路径。
5. **禁止只写"核心环节"**：`整体架构.md` 里列了多少个环节，就必须派生子 Agent 生成多少个，一个都不能少。
6. **实体模型也必须采用多 Agent**：`实体模型总览.md` 里列了多少个实体，就必须为**每个实体独立启动一个子 Agent**生成对应的 `{实体}.md`，禁止主 Agent 自己批量硬写。
7. **禁止空目录**：mkdir 了目录就必须往里写文档，不能只建空壳。
8. **禁止回头补**：每个子 Agent 在写 `整体逻辑.md` 或 `{实体}.md` 后，必须**立刻在同一个对话上下文里**写完所有关联的附属文档，不允许"回头再补"。
9. **校验必须通过命令输出**：不能说"校验通过"，必须执行 `find` 命令并把结果晒出来证明真的通过了。
10. **禁止预生成 05-自我进化 文件**：只能建空目录，任何 `.md` 都不许写。
11. **循环执行**：写不完、校验不过，就一直写，禁止以"篇幅不够""先这样吧"结束。
12. **禁止主会话权衡绕过**：不得以**任何**理由在主会话里用 `write`（或等价编辑工具）直接生成 `02-领域认知/{环节}/整体逻辑.md`、同目录下任意 `{子环节}.md`、或 `03-实体模型/{实体}.md`。包括但不限于：**任务太复杂 / 环节太多 / 怕超时 / 上下文将尽 / 先产出核心或范本 / 直接写更快 / skill 太长先简做 / 没有名为 Agent 的工具 / 目标只是子模块或文件很少（如「仅约 50 个 Java 文件」）/ 认为主会话一人足以读完写完**。正确做法是：**分批或并行调用 `task`**（或平台等价委派），由 subagent 在**子会话**中写完该环节或该实体的全部约定文件；主会话只做骨架、`整体架构.md`、`实体模型总览.md`、启动 `task`、汇总校验与根 `SKILL.md`。

## 反规避声明（与执行铁律同等效力）

下列话术在规范上**不成立**，模型**不得**据此改变执行路径；若输出中出现「我本应用 subagent，但……」式自我豁免，视为**未遵守本技能**：

| 常见自我豁免（禁止） | 正确做法 |
|---------------------|----------|
| "Given the complexity, I'll directly create the essential documents." | 复杂度再高也**不得**主会话代写环节/实体细节；**只增加 `task` 调用次数或并行批次数**。 |
| "I'll write the key domains first, then use subagents later." | **禁止先写后补委派**；未 `task` 则**不得**在 `{环节}/` 下出现 `整体逻辑.md` 或子环节 `.md`。 |
| "No Agent tool, so I'll do it inline." | 使用 **`task` 工具**委派 **subagent**（见上文「子 Agent 启动方式」）；无 `task` 则换**平台文档载明的委派方式**，**禁止**退化为单会话硬写。 |
| "Too many domains to spawn agents." | **分批并行** `task`（如每批 3～5 个）；环节数与 `task` 次数**一一对应**，不可合并为由主会话撰写。 |
| "It's a small module / only ~N source files, I'll do everything in the main session." / 「子模块很小，主 Agent 自己生成即可。」 | **无效**。规模小**不减免**委派：`整体架构.md` 列了几个环节就要几次环节 `task`，有几个实体就要几次实体 `task`；小模块只意味着单次 subagent 上下文更宽裕，**不是**省略 subagent 的理由。 |

**主会话写前硬门槛**：在调用 `write` 写入某路径前自检——若路径匹配 `{版本}/02-领域认知/[^/]+/(整体逻辑\.md|[^/]+\.md)` 且该文件**不是**`整体架构.md`，或匹配 `{版本}/03-实体模型/` 下**除** `实体模型总览.md` 外的 `.md`，则**必须先**已对该环节或实体发起 **`task`**；否则**禁止写入**，下一步只能是发起 `task`。

## 执行架构：主 Agent + 子 Agent

> 这是本技能的核心执行机制。**严禁**在一个对话上下文（主会话）内独自完成所有环节或实体的细节文档；**也严禁**以「先完成再优化」为借口在主会话里预先写入这些细节文件。

### 为什么必须拆分

webapp 类项目通常包含 15-30 个业务环节、10-20 个数据实体。若由单个 Agent 一次性完成，会出现以下致命问题：
- **上下文耗尽**：后 10 个环节/实体变成只有 30 行的空壳文档
- **源码读不透**：前面还能追踪调用链，后面只能看一眼类名就写
- **校验走过场**：最后没有精力做真正的命令输出校验

因此，必须采用 **主 Agent 统筹 + 子 Agent 隔离执行** 的架构。**02-领域认知**和**03-实体模型**都必须拆分给子 Agent。

**单模块 / 小仓库无例外**：即使本次 `static_package` 只含 `dts-server` 一类子模块、Java 文件数量有限，也**必须**按 `整体架构.md` 中的环节列表**逐个** `task` subagent 写 `02-领域认知/{环节}/`，并按 `实体模型总览.md`**逐个** `task` 写 `{实体}.md`。禁止出现「模块小，我直接在主会话里从步骤 1 写到步骤 7」的捷径。

### 主 Agent 职责

1. **生成项目骨架**：
   - 生成 `{版本目录}/01-项目总览/` 的所有文档
   - 生成 `{版本目录}/02-领域认知/整体架构.md`
   - 生成 `{版本目录}/03-实体模型/实体模型总览.md`
   - 为 `04-场景能力/` 生成目录结构（如只需要目录）
   - 创建 `05-自我进化/` 的空目录
   - 生成 **skill 根目录 `SKILL.md`**：基于 `templates/SKILL-template.md`，包含版本列表和四场景路由。这是最终产物，**不可遗漏**。

2. **为每个环节启动子 Agent**：
   - 根据 `整体架构.md` 中的环节列表，**逐个或批量并行**启动子 Agent
   - 向子 Agent 传递以下上下文：
     - 环节名称和核心职责
     - `static_package/` 中对应的源码目录路径
     - 输出目录路径（精确到 `{版本目录}/02-领域认知/{环节名}/`）
     - 指标文件中与本环节相关的指标片段

3. **为每个实体启动子 Agent**：
   - 根据 `实体模型总览.md` 中的实体列表，**逐个或批量并行**启动子 Agent
   - 向子 Agent 传递以下上下文：
     - 实体名称和业务含义
     - `static_package/` 中该实体对应的源码文件路径（如 PO/DAO/VO 类）
     - 输出目录路径（精确到 `{版本目录}/03-实体模型/`）
     - `02-领域认知/` 中该实体的来源环节和子环节信息

4. **最终合并校验**：
   - 等所有子 Agent 返回后，执行全局校验
   - 检查每个环节和实体的输出是否符合"最低内容标准"
   - 汇总所有结果，生成根 `SKILL.md`

**主 Agent 严禁做的事**：
- 严禁主 Agent 自己写任何 `02-领域认知/{环节}/整体逻辑.md` 或子环节 `.md`
- 严禁主 Agent 自己写任何 `03-实体模型/{实体}.md`
- 严禁主 Agent 在启动子 Agent 前就把所有目录建完空着（可以先建目录，但子 Agent 负责往里写）

### 子 Agent 职责（边界极为清晰）

每个子 Agent 只负责**一个**环节，必须完成以下闭环：

#### 阶段 1：源码探测与全量读取
1. 用 `find` 命令扫描该环节对应的源码目录，列出所有文件
2. **全量读取**入口层文件（HTTP handler / controller / router / gateway 等）
3. **追踪调用链**：从每个入口文件的核心方法出发，递归读取其调用的业务逻辑实现 → 数据持久化实现 → 外部调用边界实现
4. 读取到存储层或外部系统边界为止
5. 输出 `已读取源码文件清单`（必须包含相对路径和读取到的核心方法列表）

#### 阶段 2：生成 `整体逻辑.md`
基于真实读取的源码，按照 `templates/02-领域认知/整体逻辑.md` 模板生成：
- 环节概述（必须基于源码，禁止脑补）
- 子环节总览（每声明一个子环节，后面就必须写一个对应的 `.md`）
- 核心数据流程（必须精确到 `{类}.{方法}`，必须有分支和异常路径）
- 黄金指标、非黄金指标、常见故障模式、限流降级、下游关联、配置参数

#### 阶段 3：物理阻断式生成子环节文件
- `整体逻辑.md` 里写了几行子环节，就**立刻停止写整体逻辑**，转身去写对应的 `{子环节}.md`
- 所有子环节 `.md` 必须在**同一个子 Agent 对话上下文**内写完
- 子环节 `.md` 必须符合 `templates/02-领域认知/子环节.md` 模板

#### 阶段 4：本地校验与自证
子 Agent 必须在退出前执行以下校验，并把命令输出贴在返回消息里：
1. `find {输出目录}/02-领域认知/{环节}/ -type f -name "*.md" | sort` —— 证明文件确实生成了
2. 数一下 `.md` 文件数量，与 `整体逻辑.md` 中声明的子环节数量对比
3. 如果数量不匹配，**立即补全缺失文件**，不得声称"已完成"

### 子 Agent 启动方式（OpenCode：`task` 工具 → subagent）

**术语对齐（OpenCode）**：主会话中的 **primary agent** 通过 **`task` 工具** 委派工作；被调用方是配置为 **`mode: subagent`** 的子智能体（官方文档称 **subagent**）。本文中的「子 Agent」即此类 subagent。**不存在**名为 `Agent` 的委派工具；若技能旧版写「`Agent` 工具」，应理解为 **`task` 工具**。

- **`task`**：运行时提供的委派工具（Task tool），用于创建/恢复子会话并下发任务。  
- **`subagent`**：接受 `task` 委托的执行方类型（以及你在 `opencode.json` 或 agents 目录里配置的具体名称，如内置 `general`、`explore` 或自建环节专用 subagent）。

主 Agent 每环节至少调用一次 `task`（可分批并行）。参数名以当前 OpenCode 的 Task 工具 schema 为准，语义上须包含：**目标 subagent**、**任务简述**、**完整 prompt**（下块模板替换占位符后整段传入）。

```
你是 root-skills-creator 的环节级子 Agent，专门负责生成单个业务环节的详细认知文档。

你的任务：
1. 读取 {static_package_path}/src/.../{环节包名}/ 下的所有源码文件
2. 追踪调用链：入口层 → 业务逻辑层 → 数据持久化层/外部调用边界
3. 生成 {output_dir}/02-领域认知/{环节名}/整体逻辑.md
4. 生成 {output_dir}/02-领域认知/{环节名}/{子环节1}.md、{子环节2}.md 等所有子环节文件
5. 执行 find 命令校验，确保文件数量和名称与整体逻辑.md 中声明的一致

你必须遵守的约束：
- 禁止占位符：所有类名、方法名、行号必须来自真实源码
- 禁止大阶段概括：流程图必须拆解到类.方法级别，必须有 if/else 分支和异常降级路径
- 禁止回头补：所有子环节必须在同一个上下文内写完
- 禁止通过估算写行号：行号必须基于 Read 工具返回的 cat -n 格式

相关指标（供参考）：
{指标片段}
```

若运行环境无 `task` 工具，须使用该平台**等价的子会话委派能力**；禁止以「找不到委派工具」为由由主会话代写 `整体逻辑.md` 或子环节 `.md`。

### 子 Agent 执行建议

- **串行 vs 并行**：
  - 如果环节数量 ≤ 5，可以串行启动
  - 如果环节数量 > 5，建议**分批并行**启动（例如每批 3-5 个），避免系统排队过长
- **失败重试**：若子 Agent 返回"文件缺失"或"内容太简略"，主 Agent 应重新启动该子 Agent，并明确要求"补全缺失文件"或"增加流程细节"

### 实体模型子 Agent 职责（每个实体独立一个子 Agent）

每个实体子 Agent 只负责**一个**实体，必须完成以下闭环：

#### 阶段 1：源码定位与读取
1. 用 `find` 或 `grep` 命令在 `static_package/` 中定位该实体对应的源码文件：
   - PO/Entity 类（字段定义）
   - DAO/Mapper 类（数据访问）
   - VO/DTO 类（传输对象）
   - 涉及该实体的 Service 方法
2. **全量读取**上述源码文件，提取字段定义、方法签名、关联关系
3. 从 `02-领域认知/` 中追溯该实体的来源环节和子环节
4. 输出 `已读取源码文件清单`（必须包含相对路径和读取到的核心类/方法）

#### 阶段 2：生成 `{实体}.md`
基于真实读取的源码和来源追溯，按照 `templates/03-实体模型/实体.md` 模板生成：
- **实体定义和业务含义**（基于源码注释和命名）
- **字段清单**：每个字段必须标注来源环节、来源子环节、产生时机
- **生命周期**：创建、更新、销毁涉及的环节/方法
- **查询方式**：主键、索引、关联查询（基于 DAO/Mapper 方法）
- **相关指标**：可查询的指标列表（从指标文件中提取与该实体相关的）

#### 阶段 3：本地校验与自证
子 Agent 必须在退出前执行以下校验：
1. `find {输出目录}/03-实体模型/ -type f -name "{实体名}.md"` —— 证明文件确实生成了
2. 读取生成的 `{实体}.md`，确认字段数量与源码中 PO 类字段数量一致（或差异有明确说明）
3. 确认每个字段的"来源环节"和"来源子环节"能在 `02-领域认知/` 中找到对应

### 实体模型子 Agent 启动方式（OpenCode：`task` 工具 → subagent）

与「环节子 Agent」相同：主 Agent 通过 **`task` 工具** 选择目标 **subagent**，每实体至少一次。参数以 OpenCode Task 工具 schema 为准；**完整 prompt** 按下述模板替换占位符后传入。

```
你是 root-skills-creator 的实体级子 Agent，专门负责生成单个数据实体的详细模型文档。

你的任务：
1. 在 {static_package_path} 中搜索并读取与 {实体名} 相关的所有源码文件（PO/DAO/VO/Service）
2. 追溯该实体在 02-领域认知/ 中的来源环节和子环节
3. 生成 {output_dir}/03-实体模型/{实体名}.md
4. 执行 find 命令校验，确保文件生成且字段完整

实体信息：
- 实体名称：{实体名}
- 业务含义：{业务含义}
- 来源环节：{来源环节}
- 相关表名/类名：{相关类名}

你必须遵守的约束：
- 禁止占位符：所有字段名、类名、方法名必须来自真实源码
- 禁止遗漏字段：PO 类中定义的字段必须在文档中全部列出
- 字段来源必须可追溯：每个字段的"来源环节"必须能在 02-领域认知/ 中找到

相关源码路径（供参考）：
{源码路径提示}
```

### 主 Agent 验收标准

主 Agent 收到所有子 Agent 返回后，必须执行**全局验收**：

**02-领域认知 验收**：
1. **目录完整性**：`find 02-领域认知/ -maxdepth 1 -type d | wc -l` 应与 `整体架构.md` 中的环节数一致
2. **文件完整性**：`find 02-领域认知/ -type f -name "*.md" | sort`，检查是否有空目录
3. **内容深度抽查**：随机读取 2-3 个 `整体逻辑.md`，检查流程图是否有方法级精度和分支异常路径
4. **子环节对齐**：检查 `整体逻辑.md` 中声明的子环节名称是否都有对应的 `.md` 文件

**03-实体模型 验收**：
5. **实体数量一致性**：`find 03-实体模型/ -type f -name "*.md" | wc -l` 应与 `实体模型总览.md` 中声明的实体数量一致（`实体模型总览.md` 本身除外）
6. **实体文件完整性**：执行 `find 03-实体模型/ -type f -name "*.md" | sort`，检查 `实体模型总览.md` 中列出的每个实体是否都有对应的 `.md` 文件
7. **字段完整性抽查**：随机读取 1-2 个 `{实体}.md`，抽查字段数量是否与源码 PO 类一致，字段来源是否可追溯

任何一项不通过，必须定位到具体环节或实体，重新派生子 Agent 补全。

## 强制生成执行流程（必须逐条执行，禁止跳跃、禁止批量省略、禁止以"篇幅限制"为由跳过）

> **执行主体划分**：
> - 主 Agent 只负责 `01-项目总览/`、`02-领域认知/整体架构.md`、`03-实体模型/实体模型总览.md`、版本目录骨架以及启动子 Agent
> - **所有 `02-领域认知/{环节}/` 下的细节文档必须由子 Agent 生成**。主 Agent 严禁自己写 `整体逻辑.md` 或子环节 `.md`
> - **所有 `03-实体模型/{实体}.md` 必须由子 Agent 生成**。主 Agent 严禁自己写实体详情文档

### 阶段 1：主 Agent 执行规则

0. **准备 `static_package/`（若由本流程拷贝或同步源码）**：只收录**生产/主工程**源码，**禁止**放入测试代码。须排除（按仓库结构裁剪，未列到的同类路径一并排除）：`src/test/`、`src/test/java`、`src/test/resources`、`androidTest/`、`ios/**/Tests/`、`__tests__/`、`**/test/**`（若仅为测试树）、`**/*Test.java`、`**/*Tests.java`、`**/*IT.java`、`**/*.spec.ts`、`**/*.test.ts`、`e2e/`、`fixtures/`（若仅服务测试）等。若 `static_package` 由上游产物提供，主 Agent 须确认其中**无**上述测试树后再进入扫描与写文档。
1. **扫描源码根目录**：用 `find` 命令输出 `static_package/` 的实际包结构
2. **生成 `01-项目总览/` 文档**
3. **生成 `02-领域认知/整体架构.md`**：基于源码扫描结果识别环节，禁止脑补
4. **为每个环节启动子 Agent**：`整体架构.md` 里列了多少个环节，就必须启动多少个子 Agent
5. **生成 `03-实体模型/实体模型总览.md`**：基于源码中的 PO/Entity 类识别数据实体，禁止脑补
6. **为每个实体启动子 Agent**：`实体模型总览.md` 里列了多少个实体，就必须启动多少个子 Agent
7. **等待并收集所有子 Agent 结果**（环节子 Agent + 实体子 Agent）
8. **执行全局校验**（见下方"主 Agent 全局验收"）
9. **生成根 `SKILL.md` 和版本索引**：基于 `templates/SKILL-template.md` 生成 skill 根目录下的 `SKILL.md`，包含版本列表和四场景路由。**此步骤不可跳过**，即使前面所有版本目录内容都已正确生成，也必须输出根 `SKILL.md`。

### 阶段 2：领域认知子 Agent 执行规则

每个子 Agent 只负责**一个**环节，必须严格遵守以下规则：

1. **禁止一次性输出多个环节**：子 Agent 只能写自己被分配的那个环节
2. **生成前公示源码读取清单**：在写任何文档之前，必须先输出以下内容（禁止直接开始写文档）：
   ```
   【源码读取清单 - {环节名称}】
   本次读取了以下源码文件（基于 static_package/）：
   1. {相对路径1} - {类名}.{方法名} 等 {N} 个核心方法
   2. {相对路径2} - {类名}.{方法名} 等 {N} 个核心方法
   ...
   读取层级覆盖：入口层 {N} 个 / 业务逻辑层 {N} 个 / 数据访问层 {N} 个 / 外部调用层 {N} 个
   ```
3. **生成中保持一一对应**：
   - 先写 `整体逻辑.md` → 立刻检查里面声明的子环节 → 立刻逐个写对应的 `{子环节}.md`
   - 不允许"先写整体逻辑，回头再补子环节"这种分离操作
4. **生成后逐项自检**：该环节的文档写完后，必须立即执行以下自检（以文本形式输出结果）：
   ```
   【环节自检 - {环节名称}】
   - [ ] 整体逻辑.md 已生成
   - [ ] 子环节总数：声明了 {N} 个，实际生成了 {M} 个，缺失 {X} 个 → 若 X>0 立即补全
   - [ ] 若未拆分子环节，细节文档数量 >= 2：当前 {K} 个 → 若 K<2 立即补全
   - [ ] 流程图包含至少 1 个显式分支（if/else/switch）和 1 个异常/降级路径
   ```
5. **返回生成结果**：子 Agent 完成自检后，向主 Agent 汇报：
   - 生成的文件清单（含完整路径）
   - `find` 命令的输出截图
   - 自检结果

### 阶段 3：实体模型子 Agent 执行规则

每个实体子 Agent 只负责**一个**实体，必须严格遵守以下规则：

1. **禁止一次性输出多个实体**：子 Agent 只能写自己被分配的那个实体
2. **生成前公示源码读取清单**：在写任何文档之前，必须先输出以下内容：
   ```
   【源码读取清单 - {实体名称}】
   本次读取了以下源码文件（基于 static_package/）：
   1. {PO类路径} - {字段数量} 个字段
   2. {DAO/Mapper路径} - {查询方法数量} 个查询方法
   3. {VO/DTO路径} - {字段数量} 个字段
   ...
   字段来源追溯：已关联到 02-领域认知/{环节}/{子环节}.md
   ```
3. **生成要求**：
   - 基于 `templates/03-实体模型/实体.md` 模板生成
   - **字段必须完整**：PO 类中定义的每个字段都必须在文档中列出
   - **来源必须追溯**：每个字段的"来源环节"和"来源子环节"必须能在 `02-领域认知/` 中找到
4. **生成后逐项自检**：该实体的文档写完后，必须立即执行以下自检：
   ```
   【实体自检 - {实体名称}】
   - [ ] {实体名称}.md 已生成
   - [ ] 字段总数：PO 类定义了 {N} 个，文档中列出了 {M} 个，缺失 {X} 个 → 若 X>0 立即补全
   - [ ] 字段来源可追溯：已在 02-领域认知/ 中验证每个字段的来源环节
   ```
5. **返回生成结果**：子 Agent 完成自检后，向主 Agent 汇报：
   - 生成的文件路径
   - `find` 命令的输出截图
   - 自检结果

### 强制工具使用规则（关键）

为了证明你真的执行了源码读取和校验，**你必须在关键步骤使用系统命令（Bash/Find/Grep 等）探测文件系统，并将命令结果作为你下一步动作的证据**。禁止纯文本声称"我已经读了""我已经校验了"而不提供命令输出。

#### 规则 A：主 Agent —— 写整体架构.md 之前
必须先用 `find` 命令扫描 `static_package/` 的源码根目录，输出实际的包结构和文件数量。示例：
```bash
find static_package/src/main/java/com/databuff/webapp -maxdepth 1 -type d | sort
```
基于这个真实输出，识别环节，禁止脑补不存在或遗漏已存在的模块。

#### 规则 B：子 Agent —— 写环节之前
子 Agent 被启动后，必须先用 `find` 命令探测该环节的源码目录，确认有多少个入口文件/业务逻辑实现/数据持久化实现等文件。示例：
```bash
find static_package/src/.../{环节包名} -type f -name "*.java" | sort
```
然后逐个读取核心文件。读取清单中的每个文件必须在上述 `find` 命令的输出中有体现。

#### 规则 C：子 Agent —— 写环节之后
必须用 `find` 命令检查该环节目录下实际生成了多少个 `.md` 文件，并与 `整体逻辑.md` 中的声明对比。示例：
```bash
find 02-领域认知/{环节}/ -type f -name "*.md" | sort
```
如果数量不匹配，子 Agent 必须立即补全缺失文件，不得向主 Agent 汇报"已完成"。

#### 规则 D：主 Agent —— 全局验收之前

**验证 02-领域认知**：
```bash
# 检查环节目录数量是否与整体架构.md 一致
find 02-领域认知/ -maxdepth 1 -type d | sort

# 检查是否有空目录（没有 .md 文件的目录）
find 02-领域认知/ -type d -empty
```
如果存在空目录或缺失环节，必须重新启动对应子 Agent。

**验证 03-实体模型**：
```bash
# 检查实体文件数量是否与实体模型总览.md 一致
find 03-实体模型/ -type f -name "*.md" | sort

# 检查是否有空目录
find 03-实体模型/ -type d -empty
```
如果实体文件缺失，必须重新启动对应实体子 Agent。
如果数量不匹配，**立即停止并补全缺失文件**，不得进入下一个环节。

#### 规则 E：实体模型子 Agent —— 写实体之前
子 Agent 被启动后，必须先用 `find`/`grep` 命令定位该实体相关的源码文件：
```bash
# 搜索实体 PO 类
grep -r "class {实体名}" static_package/src --include="*.java" | grep -i "entity\|po\|model"

# 搜索该实体相关的 DAO/Mapper
find static_package/src -name "*{实体名}*Mapper.java" -o -name "*{实体名}*Dao.java" | sort
```
然后读取 PO 类获取所有字段，读取 DAO 类获取查询方法。

#### 规则 F：实体模型子 Agent —— 写实体之后
必须用 `find` 命令检查该实体文件是否生成，并与源码 PO 类的字段数量对比：
```bash
# 检查实体文件是否生成
find 03-实体模型/ -name "{实体名}.md"
```
如果文件未生成，必须立即补全，不得向主 Agent 汇报"已完成"。

#### 规则 G：所有校验必须通过命令输出
自检不能只是你在对话中说"校验通过"，必须是：
1. 你运行了命令
2. 输出了命令结果（如文件列表、数量统计）
3. 基于结果说明是否符合要求
4. 如果不符合，立即执行补全操作

### 失败案例警示（ why this matters ）

以下是一个真实发生的不合格生成案例。如果你重蹈覆辙，输出将被视为垃圾：

**错误行为 1：主 Agent 不派生子 Agent，自己硬写 20 个环节，导致后 10 个全是 30 行空壳**
- 后果：`audit/`、`cockpit/`、`agentbrain/` 等环节只有基本信息表格，没有流程图、没有子环节文件。
- 你的做法：主 Agent 必须只为每个环节启动独立的子 Agent，严禁自己写 `02-领域认知/{环节}/` 下的任何细节文档。

**错误行为 2：子 Agent 读了 3 个入口文件就停手，没有追踪到业务逻辑层和数据持久化层**
- 后果：流程图里只有 `[入口Handler] → [业务Service] → [InfluxDB]`，中间怎么构建查询、怎么转换数据、异常怎么处理全部缺失。
- 你的做法：子 Agent 必须从每个入口方法出发，沿着调用链递归读取，直到触及存储层或外部系统边界。

**错误行为 3：`整体逻辑.md` 里写了 3 个子环节，但一个都没写对应的 `.md` 文件**
- 后果：关联约束断裂，下游排障时找不到子环节细节。
- 你的做法：子 Agent 写 `整体逻辑.md` 时声明了几种子环节，就必须在同一个上下文里把每个子环节 `.md` 写完。

**错误行为 4：处理流程只有 5 个大阶段，没有方法签名、没有分支**
```
[用户输入] → [入口层参数校验] → [业务逻辑层构建查询] → [数据持久化层查询] → [结果组装] → [返回]
```
- 后果：这个流程图对故障定位毫无帮助，看不出哪里会超时、哪里会异常、哪个配置参数影响查询。
- 你的做法：每个方框必须是 `{类名}.{方法名}`，必须有 `if/else` 分支和异常降级路径。

**错误行为 5：自己运行了 `ls` 就宣布"校验通过"**
- 后果：明明缺失了 16 个文件，却声称"已校验"。
- 你的做法：运行 `find` 命令后，必须逐条数数对比，缺失的文件必须立即补，不能嘴硬。

**错误行为 6：生成 `故障排查.md` 时自由发挥，不直接复制模板**
- 后果：下游 LLM 找不到正确工具名和参数，排障流程断裂。
- 你的做法：详见 `04-场景能力/ 故障排查.md（按版本，不共享）` 的生成约束——**直接复制模板，严禁任何改写、增补或删减。**

**错误行为 7：主 Agent 不派生子 Agent，自己硬写 10 个实体，导致只有 2 个有字段详情，其他全是空壳**
- 后果：`实体模型总览.md` 里列了 15 个实体，但只有 2 个有 `{实体}.md` 文件，其他实体缺失字段清单、生命周期、查询方式等关键信息，问数场景无法使用。
- 你的做法：
  1. 主 Agent 必须只为每个实体启动独立的子 Agent，严禁自己写 `03-实体模型/{实体}.md`。
  2. `实体模型总览.md` 里列了多少个实体，就必须启动多少个子 Agent。
  3. 实体子 Agent 必须读取 PO 类获取所有字段，读取 DAO 类获取查询方法，确保字段完整、来源可追溯。

**错误行为 8：实体子 Agent 漏写字段，只写了 5 个但 PO 类定义了 20 个**
- 后果：下游问数时找不到字段，用户查询失败。
- 你的做法：
  1. 实体子 Agent 必须在写文档前读取 PO 类，统计字段总数。
  2. 写文档后自查：文档中列出的字段数必须等于 PO 类字段数（或差异有明确说明，如"冗余字段已排除"）。
  3. 主 Agent 验收时抽查：随机选 1-2 个实体，对比 `{实体}.md` 和 PO 源码的字段数量。

**错误行为 9：口头上承认应起 subagent，却以「复杂度 / 时间 / 先交核心」为由在主会话里 `write` 环节或实体细节**
- 典型表述（均视为违规）：*"I should launch sub-agents for each domain, but given the complexity… I'll directly create the essential documents."*、*「环节太多，我先在主会话写一版」*。
- 后果：与错误行为 1、7 相同，产出不可信，且破坏「一环节/一实体一子会话」的隔离。
- 你的做法：**禁止**在主会话对上述路径 `write`；**只能**增加 `task` 调用（可分批并行）。若已误写，**删除**误写文件后按铁律第 12 条与「反规避声明」重做。

**错误行为 10：以「子模块小 / 源码文件少」为由省略 subagent，主会话从总览一路写到根 SKILL.md**
- 典型表述：*"Since dts-server is a relatively small module (only ~50 Java files), I'll … let me start generating documents."*、*「单模块文件不多，主 Agent 能一次做完」*。
- 后果：与错误行为 1 相同；且小模块往往更缺深度分析，主会话包办会放大「流程图只有大阶段、子环节缺失」问题。
- 你的做法：**环节数、实体数与项目规模无关**；有几个环节就几次环节 `task`，有几个实体就几次实体 `task`。小模块仅减少单次 subagent 的阅读负担，**不减少** `task` 次数。

如果你不想产出垃圾，就不要做以上任何一件事。

### 内容表达约束（新增）

为了提升认知文档的可读性和排障效率，子环节 `.md` 必须遵守以下表达规则：

1. **禁止粘贴原始源码**
   - 严禁在 `.md` 中插入完整的 Java 类代码块、带注解的方法签名块（如 `@Api @RestController public class Xxx` 或 `public CommonResponse<Object> upgradePackageUpload(...)`）
   - 严禁整段复制源码中的 import 声明、类注释、字段定义
   - **正确做法**：用精炼的文字描述方法的功能、参数含义、返回值、关键逻辑。源码只作为你理解的输入，不作为输出的内容。

2. **方法名必须配中文释义**
   - 在流程图、类结构表、调用链中，每个 `{类名}.{方法名}` 旁边**必须紧跟括号中文释义**
   - **示例**：`getUpdateProgress() (获取升级进度) `、`AgentUpgradeService.checkPackage() (校验升级包完整性)`
   - **禁止**：只写 `getUpdateProgress()` 而没有任何中文说明。

3. **流程图禁止出现原始代码语法**
   - 流程图中的每个步骤必须是**业务语义描述**，不得出现 `// 上传升级包` 这种源码注释、不得出现 `@ApiOperation` 这种注解描述。

#### 源码分析深度要求（生成 02-领域认知 前强制执行）

在生成每个 `环节/` 及其内部的 `整体逻辑.md`、`{子环节}.md` 之前，**必须先完成对该环节源码的深度扫描和核心文件读取**，具体要求如下：

1. **源码定位**：
   - 通过 `static_package/` 目录结构，定位该环节对应的代码目录（通常与环节名称或核心类包名对应）
   - 扫描该目录下的所有 Java/Go/Python 等源码文件，识别出属于该环节的核心类

2. **核心文件强制读取（全量入口 + 调用链追踪）**：
   - **入口层：全量读取**：扫描并读取该环节下**所有**入口文件（即暴露给外部的接口层，如 HTTP handler、路由层、controller、gateway、API endpoint 等）。如果某个目录下有 10 个入口文件，则必须全部读完，禁止只挑一部分。
   - **按调用链全量追踪**：读取每个入口文件后，必须追踪其所有公共/核心方法调用的下游文件，一层一层向下读取，直到触及边界为止：
     - **核心业务处理层**：被入口文件直接调用的业务逻辑实现（如 service、usecase、handler、manager、core processor 等）→ 全部读取
     - **数据持久化层**：被业务逻辑调用的数据存储访问实现（如 dao、repository、mapper、store、data access 等）→ 全部读取
     - **外部调用边界**：调用外部系统、第三方服务、消息队列、数据库等（如 client、connector、producer、adapter 等）→ 全部读取
   - **禁止抽样读取**：不得因"文件太多"而只选 5 个读取。同一层级下、被调用链触及的所有文件都必须读取。
   - **边界条件**：读取到数据持久化层或直接遇到外部调用边界为止。

   **示例**：分析 "APM 链路追踪" 环节时：
   - **入口层全量读取**：`apm/handler/TraceHandler.java`、`apm/handler/SpanHandler.java`、`apm/handler/TopologyHandler.java`...（该目录下所有暴露给外部的接口文件，可能表现为 controller、router、gateway、endpoint 等形式，必须全部读完）
   - **调用链追踪**：从每个入口文件的每个核心方法出发，追踪被调用的业务逻辑文件：
     - `apm/processor/TraceQueryProcessor.java`、`apm/processor/TraceAnalysisProcessor.java`、`apm/processor/SpanProcessor.java`...（所有被入口文件直接或间接调用的业务处理实现，可能表现为 service、usecase、manager、handler 等形式，全部读完）
   - **继续向下追踪**：业务逻辑文件调用的数据访问实现（repository、dao、mapper、store 等）、缓存访问、外部存储查询等全部读完
   - **外部调用边界**：如涉及 `apm/connector/StorageConnector.java`、`apm/connector/CollectorConnector.java`（或 client、adapter、producer 等形式），也一并读完

3. **禁止脑补**：
   - **类结构**中列出的类名、包路径、核心方法列表，必须直接来源于读取的源码，禁止编造
   - **逻辑细节**中的方法签名、行号范围、输入输出参数、异常码，必须基于源码实际内容
   - **处理流程**中的每个步骤必须能映射到源码中的具体方法调用链
   - 若因源码混淆/缺失导致无法确认，需明确标注"源码不可读/缺失"，不得虚构

4. **指标与配置的源码锚定**：
   - 所有标注的【黄金指标】【非黄金指标】【配置参数】必须能在源码中找到采集点或引用点
   - 指标采集点格式：`{类名}:{方法名}:{行号}` 必须基于源码读取结果填写

5. **生成顺序**：
   - 先读源码 → 再提取类结构/调用链/处理流程 → 最后编写 Markdown 文档
   - 文档输出必须体现"从源码观察到的结果"，而非"基于常识推断的结果"

   - 若发现**任何一处**与模板不一致（除路径调整外），**立即删除当前生成的 `故障排查.md`**
   - 将模板内容**原封不动**复制到 `{版本目录}/04-场景能力/故障排查.md`，只做 `03-场景能力/` → `04-场景能力/` 的替换
   - **禁止**在自由发挥版本上删改、修补或重写

### 主 Agent —— 校验步骤 3：环节双向一致性

1. 读取 `02-领域认知/整体架构.md` 中的"环节定义总览"表格，提取所有列出的环节名称列表 `A`。
2. 扫描 `02-领域认知/` 下所有子目录（排除 `整体架构.md` 本身），得到实际生成的环节目录列表 `B`。
3. **必须满足 `A == B`（集合相等）**：
   - 若 `A` 中有某个环节在 `B` 中缺失 → **立即为该环节重新启动子 Agent**生成 `整体逻辑.md` 和至少 1 个子环节 `.md` 文件
   - 若 `B` 中有某个环节在 `A` 中缺失 → **立即在"环节定义总览"中补充定义**，或删除该多余目录
4. **空目录检查**：执行 `find 02-领域认知/ -type d -empty`，若存在空目录 → **立即向该空目录对应的环节重新派生子 Agent**

### 子 Agent / 主 Agent —— 校验步骤 4：子环节完整性

对每个 `{版本目录}/02-领域认知/{环节}/` 目录执行以下检查：

1. **列出环节 `X` 在 `整体逻辑.md` 的"子环节总览"表格中声明的所有子环节名称列表 `S1`**
2. **列出环节 `X` 目录下除 `整体逻辑.md` 以外的所有 `.md` 文件名称列表 `S2`**
3. **判断规则**：
   - 若 `S1` 非空：必须满足 `S1 ⊆ S2`（每个声明的子环节都有对应文件）。若有缺失 → **立即生成缺失的子环节 `.md` 文件**
   - 若 `S1` 为空（该环节暂未拆分子环节）：必须满足 `|S2| >= 2`（至少生成 2 份细节文档覆盖不同的关键数据流程或逻辑面）。若不足 2 个 → **立即补充生成到至少 2 份**

### 子 Agent / 主 Agent —— 校验步骤 5：处理流程深度抽查

随机（或按字母顺序前 3 个）挑选 `02-领域认知/{环节}/{子环节}.md` 文件进行检查：

- [ ] **处理流程是否拆解到方法/操作级别**？如果还是 `[步骤1: 语义解析] → [步骤2: 查询构建]` 这种 3-5 个大阶段 → **退回重写**
- [ ] 流程图中是否包含**至少 1 个条件分支或异常分支**？如果是一条直线 → **退回重写**
- [ ] 每个步骤是否标注了**具体类名.方法名**（或等效的操作标识）？如果只有"参数校验""结果组装"等模糊描述 → **退回补充**
- [ ] 是否标注了至少 1 个**指标**或**配置参数**在流程中的位置？如果没有 → **退回补充**

### 子 Agent / 主 Agent —— 校验步骤 6：源码映射真实性

抽查至少 2 个子环节 `.md` 文件中的以下内容：

- [ ] **核心类清单**中的类名、包路径是否直接来自 `static_package/` 的源码？如果使用了基于常识的占位符（如 `XxxProcessor` / `XxxHandler` 这种没有对应源码文件的） → **退回重写**
- [ ] **核心方法列表**中的方法名和行号是否为真实读取结果？如果行号写的是 `100-200` 这种明显估算的区间 → **退回修正**
- [ ] **指标采集点**格式 `{类名}:{方法名}:{行号}` 是否能在源码中找到依据？如果不能 → **退回修正或删除该指标**

### 主 Agent —— 校验步骤 7：实体模型完整性（多 Agent 生成结果校验）

1. **实体数量一致性检查**：

   - 若存在缺失 → **立即为缺失的实体重新启动子 Agent 生成**

2. **实体文件生成方式检查**：

   - 若发现主 Agent 代写 → **删除该文件并重新派生子 Agent 生成**

   - 若差异过大（如缺失超过 30% 的字段）→ **退回对应实体子 Agent 补全**

### 主 Agent —— 校验步骤 8：实体-环节一致性

- [ ] 每个实体的"来源子环节"是否都能在 `02-领域认知/{环节}/{子环节}.md` 中找到处理流程的对应步骤？如果找不到映射 → **向对应环节重新派生子 Agent，补充子环节文档中的处理流程细节**

### 校验失败后的补全规则

1. **禁止跳过**：无论缺失多少文件，无论文件大小，都必须补全。
2. **禁止降级**：不得以"简化处理""合并描述"等方式降低模板要求的深度。
3. **禁止占位符**：补全内容必须基于实际源码读取结果，禁止用 `{类名}` `{方法名}` 等占位符填充后声称"这是模板"。
4. **`故障排查.md` 补全规则**：若未按模板生成，必须**删除原文件并直接复制模板内容**，禁止在原稿上删改、重写或发挥。
5. **循环校验**：补全后必须重新执行校验步骤 2-9，直到全部通过为止。
6. **子 Agent 重派机制**：由主 Agent 校验发现的任何环节级问题，必须通过**重新启动子 Agent**解决，禁止主 Agent 自己随手补几句话敷衍。
