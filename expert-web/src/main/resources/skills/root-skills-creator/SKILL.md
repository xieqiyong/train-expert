# Skill 包生成器

## 提供的信息

使用本技能时，只需要用户提供以下信息：

1. **项目名称**：要分析的项目名称
2. **项目代码路径**：要分析的项目源代码目录
3. **指标文件路径**：包含监控指标的Markdown文件（格式：## 指标名称\n描述）
4. **输出目录路径**：生成skill包的目标目录

## 生成目标

基于源码、指标说明和版本快照，生成一个多版本 skill。输出目录结构必须如下：

```text
<Skill 根目录>/
├── SKILL.md
├── <版本目录 A>/
│   ├── 故障排查思路.md              # troubleshooting-template.md（每版本一份，不共享）
│   ├── 整体架构.md
│   ├── 环节1/
│   │   ├── 整体逻辑.md                    # component-logic-template.md（必填）
│   │   ├── {子环节或逻辑单元1}.md        # component-detail-template.md（必填，与子环节一一对应）
│   │   └── {子环节或逻辑单元2}.md
│   ├── 环节2/
│   │   └── ...
│   └── static_package/
└── <版本目录 B>/
    ├── 故障排查思路.md
    └── ...
```

## 生成要求

### 1. 版本目录

- 每个版本目录代表一个独立快照，目录名可以是 tag、镜像版本、发布日期或其他可稳定标识版本的名称
- 如果能识别多个版本，则分别生成多个版本目录
- 如果没有明确版本信息，则至少生成一个默认版本目录，并在根 `SKILL.md` 中将其视为最新版本
- 不同版本目录下的 `故障排查思路.md`、`整体架构.md`、环节目录和 `static_package/` 相互独立，禁止混写

### 2. `故障排查思路.md`（按版本，不共享）

- **位置**：必须放在**每个版本目录的根下**，与 `整体架构.md` 同级，例如 `{版本目录}/故障排查思路.md`；**禁止**在 skill 根目录再放一份全局共享的 `故障排查思路.md`
- **内容**：按 `templates/troubleshooting-template.md` 生成，语义对齐原 `databuff-skill-creator` 中 `templates/skill-md-template.md`，可按该版本的项目名、指标与架构做差异化填充
- 该文件专门用于该版本的排障流程，不承担认知问答入口职责；不同版本的排障步骤、工具或指标若不一致，须在各自文件中体现，不得跨版本共用一份文档

### 3. 版本认知文档

- 每个版本目录都需要生成 `故障排查思路.md` 与 `整体架构.md`
- 每个核心环节都需要有独立目录和 `整体逻辑.md`（必须按 `templates/component-logic-template.md` 生成）
- **逻辑细节文档（强制）**：每个环节目录下除 `整体逻辑.md` 外，**必须**再生成若干 Markdown 文件，且**必须**按 `templates/component-detail-template.md` 的结构与章节顺序填充内容，不得只留空壳标题
- **与子环节一一对应（强制）**：`整体逻辑.md` 中「子环节与黄金指标」小节列出的**每一个子环节**，都必须在同一环节目录下有一份对应的逻辑细节文档；文件名与子环节名称一致（或清晰可映射的等价命名，如 `链路追踪.md` 对应子环节「链路追踪」）
- **下限**：若某环节在 `整体逻辑.md` 中暂未拆分子环节，则该环节目录下仍须至少生成 **2 份** 由 `component-detail-template.md` 展开的细节文档，分别覆盖该环节下两条不同的关键数据流程或关键逻辑面（禁止仅存在 `整体逻辑.md` 而无任何细节文档）
- 文档风格延续 `databuff-skill-creator`：聚焦架构、运行逻辑、指标、配置参数、故障模式；细节文档须写全模板中的「逻辑细节、黄金指标、非黄金指标、常见故障模式」等块，避免只有概述没有下钻

### 4. `static_package/`

- 每个版本目录下都必须保留 `static_package/`
- 该目录用于存放对应版本的源码快照、反编译结果、静态资源或原始采集材料
- **认知类问题**：必须读取该版本 `static_package/` 中的源码做深度分析与验证，不能只依据认知文档作答
- **排障**：按**当前选定版本目录**下的 `故障排查思路.md` 执行；需要代码佐证或文档不足时，读取同版本 `static_package/` 继续分析

## 根 `SKILL.md` 生成规则

根 `SKILL.md` 必须包含 YAML frontmatter，并明确说明以下行为：

1. 先选择版本号；如果用户没有明确指定，则使用最新版本
2. 如果用户要查找认知（认知类问题）：
   - 先选择版本号；如果未指定则使用最新版本
   - 在对应版本中寻找相关认知文档，形成初步理解
   - **必须**继续读取该版本 `static_package/` 中的源码进行深度分析与验证
   - **禁止**仅依据认知文档直接给出最终回答
   - 若文档结论与源码行为不一致，以源码分析结果为准
   - 最终回答须同时体现文档认知、源码事实与版本上下文
3. 如果用户要排障：
   - 在选定版本目录下读取 `故障排查思路.md`，严格按其中流程排查，并加载该版本下的详细认知文档
   - 如果需要进一步分析代码，则读取该版本 `static_package/` 中的源码继续分析

## 模板文件

生成文件时，不要把模板直接写死在根 `SKILL.md` 中，必须使用 `templates/` 目录下的独立模板文件：

- `templates/skill-template.md`：用于生成根 `SKILL.md`
- `templates/troubleshooting-template.md`：用于生成各**版本目录**下的 `故障排查思路.md`（每个版本独立一份）
- `templates/architecture-template.md`：用于生成各版本目录下的 `整体架构.md`
- `templates/component-logic-template.md`：用于生成各环节目录下的 `整体逻辑.md`
- `templates/component-detail-template.md`：用于生成各环节下的逻辑细节文档（**每个环节必填**，且与子环节或关键逻辑一一对应，见上文「逻辑细节文档（强制）」）

生成时应优先基于模板填充内容，而不是在根 `SKILL.md` 中重新拼接一套临时结构说明。生成完成后须自检：任意 `{环节}/` 目录内是否存在除 `整体逻辑.md` 以外的、符合 `component-detail-template.md` 结构的至少一份细节文件；若仅有 `整体逻辑.md` 则视为生成不合格，须补全。

## 生成约束

- 根 `SKILL.md` 只负责版本选择、认知查询入口、排障入口和版本入口导航
- 排障 SOP 不要直接写进根 `SKILL.md`，而是写入**各版本目录**下的 `故障排查思路.md`
- 根 `SKILL.md` 必须明确：**认知类问题强制**读取对应版本 `static_package/` 做源码级深度分析；排障路径在需要时读取 `static_package/`
- 若存在多个版本，必须体现“不同版本相互独立”的原则
- 文档内部禁止出现本地绝对路径和网络 URL
- 文档内部避免具体函数名、代码行号、底层实现细节；但可以保留对诊断有价值的指标名、配置参数名和高层流程名
- 环节目录结构合规：`{版本}/{环节}/整体逻辑.md` 与至少一份 `component-detail` 类细节文档并存；`整体逻辑.md` 中列出的每个子环节均有对应细节文档（无子环节列表时至少 2 份细节文档）
- **禁止**在 skill 根目录放置全局共享的 `故障排查思路.md`；排障 SOP 仅允许出现在各 `{版本目录}/故障排查思路.md`
