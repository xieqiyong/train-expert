## 场景一：架构认知 / 原理解释

用于回答"这是什么"、"如何工作"、"为什么这样设计"等认知类问题。

### 执行流程

1. **选择版本号**；如果未指定则使用最新版本
2. **读取 01-项目总览/**：
   - `技术栈与架构.md` - 了解技术栈和部署架构
   - `目录结构.md` - 了解源码组织方式
   - `核心流程图.md` - 了解系统整体数据流
3. **读取 02-领域认知/整体架构.md**：
   - 了解项目包含哪些环节
   - 了解各环节的黄金指标定义（生成时已与 `/app/upload/data` 指标体系元数据对齐）
4. **按需深入 02-领域认知/{环节}/**：
   - `整体逻辑.md` - 了解环节内子环节划分和流程
   - `{子环节}.md` - 了解具体逻辑细节
5. **读取 03-实体模型/实体模型总览.md**：
   - 了解系统有哪些核心数据实体
   - 了解实体间的关联关系
   - 了解实体与环节的映射关系
6. **按需读取 `static_package/`**（**非**每问必读的硬性前置）：
   - **通常**：`01`～`04` 中相关 **`.md` 已足够** 回答架构/原理类问题
   - **当**问题复杂、多文档矛盾、**`.md` 未说明**或需与实现逐行核对时，再读 `static_package/`，将文档与源码对比；**若**已读源码，文档与实现不一致**以源码为准**
7. **综合**文档、（必要时）源码与版本上下文，给出完整、准确的解释

## 场景三：故障排查（八步法则）

用于定位系统故障、分析异常根因。

### 执行流程

1. **选择版本号**；如果未指定则使用最新版本
2. **读取 {版本}/04-场景能力/故障排查思路.md**
3. **默认以八步法则为主路径**（**完整、按序**执行，禁止跳跃、禁止提前下结论）：

#### 第一步：明确查询时间
- 如果用户已提供 queryStartTime、queryEndTime，则直接使用
- 如果没有，调用 `getCurrentTimeRange` 获取当前查询时间范围

#### 第二步：加载配置
- 如果能获取到当前项目的配置文件则加载它（如果配置文件为空则代表没有采集对应的配置文件则忽略）

#### 第三步：全局扫描
- 加载 `02-领域认知/整体架构.md`，提取所有环节的黄金指标

#### 第四步：数据获取
- 找出所有环节的黄金指标
- 构建queryAndDrillDown的查询请求：
   - AbnormalDetail：由之前的分析结果中提取，如果没有则填null，不要随意编造
   - 构建MetricRequest
      - identifiers：即上述所有环节的黄金指标
      - queryStartTime：上述queryStartTime
      - queryEndTime：上述queryEndTime

#### 第五步：挑出有问题的环节
- 使用 queryAndDrillDown 工具分析黄金指标，找出有问题的指标
- **指标验证（必须严格执行）**：指标必须在 `[abnormalStartTime, abnormalEndTime]` 内有吻合的波动时间点才算异常
- 若某环节黄金指标异常，则标记该环节为有问题
- **tag 维度下钻（标记异常后执行）**：对每个已判定异常的 **identifier**，调用 **`findMetricCoreByIdentifier`** 读取 MetricsCore；据合法 tag 选定 **`groupBys`**；在同一 **`[abnormalStartTime, abnormalEndTime]`**、同一 entity（及若有则同一 AbnormalDetail）下再次 **`queryAndDrillDown`**（传入 **`groupBys`**，依据 **`rootCaseMaps`** 归纳主导异常的维度取值并写入结论）
- 异常指标下的rootCaseMaps
   - 如果是null代表当前指标的问题并不集中在某几个tag维度上而是所有维度都有这种问题
   - 如果不是null代表当前指标的问题集中在rootCaseMaps对应的维度上
- **执行闸门（硬约束）**：凡是已标记异常的 **identifier**，若未完成上述 tag 下钻（未成功获取 MetricsCore、未形成有效 `groupBys`、或未执行带 `groupBys` 的二次 `queryAndDrillDown`）则本次分析无效，禁止进入结论推演与最终结论输出

#### 第六步：环节的详细分析
- 对有问题的环节，加载对应的 `02-领域认知/{环节}/整体逻辑.md`，提取非黄金指标
- 按需加载 `02-领域认知/{环节}/{子环节}.md` 获取逻辑细节
- **数据定位时参考 `03-实体模型/`**：
  - 通过实体找到异常数据的具体位置
  - 追溯字段来源，确认数据产生环节
- 查询非黄金指标并进行下钻
- **tag 维度下钻（标记异常后执行）**：对每个已判定异常的 **identifier**，调用 **`findMetricCoreByIdentifier`** 读取 MetricsCore；据合法 tag 选定 **`groupBys`**；在同一 **`[abnormalStartTime, abnormalEndTime]`**、同一 entity（及若有则同一 AbnormalDetail）下再次 **`queryAndDrillDown`**（传入 **`groupBys`**，依据 **`rootCaseMaps`** 归纳主导异常的维度取值并写入结论）
- **因果链条建立**：必须描述"因为指标 A 突变导致了指标 B 的异常"，严禁孤立看待指标
- **最终验证（必须严格执行）**：所有推导出的原因，其对应指标必须在时间窗内有吻合的波动
- **在八步流程内、且仍须更深一层明确逻辑时**：若 `02-领域认知/`、`03-实体模型/` 与当步下钻**仍不足以**支撑该步判断，可读取同版本 `static_package/` 补充认知；**不**用读源码替代或打断八步的完整与顺序

#### 第七步：结论推演
- 仅基于已识别的异常指标，推理 1～3 条因果链条
- 每条链条需包含：根因指标 →（可选）中间指标 → 结果指标
- 根因判定：根因指标必须在时间窗内发生突变
- 若黄金指标在时间窗内均无突变：直接输出未发现异常，禁止假设根因
- 因果校验（必须全部满足）：机制合理、时间顺序正确、符合 Redis 架构、无更合理替代解释
- 量级门槛：若候选原因 `A` 的变化量显著小于结果 `B`（默认阈值：`delta(A) < delta(B) / 5`），`A` 不得作为根因，只能降级为促发因素或伴随现象
- 反向因果检验：必须同时对比 `A -> B` 与 `B -> A`；若后者在时间顺序、机制合理性、量级解释力上更强，则禁止输出 `A -> B` 为根因
- 案例：`connections_received` 约 `11 -> 25`（约 `+2.27x`），但 `cpu_cfs_throttled_seconds` 约 `+207x`；量级不闭合时优先判定 `CPU CFS throttling -> 事件循环受压 -> 吞吐下降/连接堆积`
- **反直觉校验（硬约束）**：当出现“吞吐/命令下降 + Redis 组件自身 CPU 下降”组合时，**不得**直接判定为“外部请求减少”；必须并列考虑“资源层限流/抢占/run queue 堵塞导致拿不到 CPU”，并进入第八步交由 `schedule` 决策下钻验证。
- 输出约束：最终仅允许一个结论，禁止多根因、模糊或猜测性结论

##### 经验总结
- 凡结论包含“风暴/激增/打满/拥塞”等事件量驱动表述时，必须同时验证该对象的请求量（次数或占比）上涨且对应性能指标恶化（耗时/延迟/队列等），否则不得将其定为根因。

### 第八步：决策是否下钻到资源层(k8s/docker/process)

**host**和**node**是同一个概念，根据实际情况进行选择，下面统一叫**host**
**决策优先级（硬约束）**：先判断是否属于性能恶化场景；若是，则必须下钻资源层，禁止直接收敛。
**路径约束（硬约束）**：第八步下钻到 `host`层时遵循双条件约束：组件层禁止直接下钻 `host`；资源层（`k8s`/`docker`/`process`）允许直接下钻 `host`（通常由 `schedule` 决策）。
**反直觉校验（硬约束）**：当出现“组件 CPU 下降 + 吞吐/命令下降”组合时，**不得**直接收敛为“外部请求减少”；必须并列评估资源层限流、CPU 抢占、run queue 堵塞等可能，并交由 `schedule` 继续资源层下钻验证。

如果判断**可能是资源层问题导致的性能恶化**，则：
- 交由 `schedule` skill 决策并继续深入资源层分析
- **性能出现恶化的场景**必须交由 `schedule` skill 决策并继续深入资源层分析，因为很可能是资源层恶化导致当前组件运行恶化
- **慢查询（slowlog/latency 异常）默认归为性能恶化场景**，必须交由 `schedule` 继续下钻资源层

如果已经找到**明确的组件级根因**，且与资源层无关，则：
- **不需要下钻**
- 直接输出最终结论和优化建议

## 场景四：巡检

用于执行系统健康检查、生成巡检报告。

### 执行流程

1. **选择版本号**；如果未指定则使用最新版本
2. **读取 {版本}/04-场景能力/巡检清单.md**
3. **按清单逐项检查**：
   - 读取 `02-领域认知/整体架构.md` 获取各环节黄金指标（与指标体系元数据黄金集合一致）
   - 读取 `03-实体模型/实体模型总览.md` 了解数据实体范围
   - 按清单定义的检查频率、预期值进行核查；**逐项覆盖全部黄金指标**，缺失则先补清单再执行
4. **数据检查时参考 `03-实体模型/`**：
   - 确认检查的数据实体
   - 通过实体生命周期了解数据产生规律
5. **异常标记**：
   - 指标偏离预期值 → 标记异常
   - 关联 `02-领域认知/{环节}/{子环节}.md` 中的故障模式
6. **生成巡检报告**：
   - 正常项汇总
   - 异常项详情（现象、可能原因、建议措施）
7. **必要时转入排障流程**

## 使用约束

### 认知类问题硬约束

- **默认**以认知文档（`01-项目总览/`、`02-领域认知/`、`03-实体模型/` 下的 **`.md`**）为主要依据
- **当**需代码级证实时（复杂问题、`.md` 未覆盖、多文档矛盾、或必须核对实现细节），再读取 `static_package/` 完成补充分析
- 若已对照源码，认知文档与 `static_package/` 中行为不一致，**以源码分析结果为准**
- 若本不应读源码即可作答，**不必**为形式感强行扫读；若**需要**读而 `static_package/` 为空或不可读，须在回答中说明该限制，并仅基于文档给出**带置信度**的结论，不得假装已完成源码验证

### 排障类问题硬约束

- **禁止**在 skill 根目录放置全局共享的 `故障排查思路.md`
- 排障 SOP **仅允许**出现在各 `{版本目录}/04-场景能力/故障排查思路.md`
- **默认**严格按**八步法则**执行，禁止跳跃、禁止提前下结论；**在八步主流程内**，若需更深逻辑清晰化且文档/数据仍不足，可再读同版本 `static_package/` 补充认知
- **必须使用实体模型进行数据定位**：通过 `03-实体模型/` 追溯字段来源，定位异常数据

### 问数类问题硬约束

- **必须**通过 `03-实体模型/` 确认实体字段定义
- **必须**追溯字段来源到 `02-领域认知/{环节}/{子环节}.md`
- 不得编造字段或指标，所有查询字段必须能在实体模型中找到
- **指标类问数**须优先查 `04-场景能力/问数语义.md` 中的「业务语义到指标的映射」，指标标识须与训练侧指标体系一致；答复用户时不要引用内部元数据路径

### 通用约束

- 根 `SKILL.md` 只负责版本选择、场景路由和约束声明
- 不要把详细排障 SOP、巡检清单、问数语义直接写在根 `SKILL.md` 中
- 若存在多个版本，必须体现"不同版本相互独立"的原则
- 文档内部禁止出现本地绝对路径和网络 URL（**例外**：本文件本条仅说明——训练生成 skill 时使用的指标体系元数据根路径为 `/app/upload/data`，运行态读取用户可见文档时勿向用户复述该路径）
