## 核心运行说明

本技能用于进行故障定位。

### 运行流程

**八步法则**
- **必须强制执行**
- **每一步都不能少，需要计数，每走一步+1，必须保证最终是9**
- **开始、中间、结束必须记录已分析的步骤、未分析的步骤**

#### 第一步：明确查询时间
- 如果已经有queryStartTime、queryEndTime，则使用 queryStartTime、queryEndTime
- 如果没有，调用工具 `getCurrentTimeRange` 方法获取当前查询时间范围

#### 第二步：加载配置
- 如果能获取到当前项目的配置文件则加载它（如果配置文件为空则代表没有采集对应的配置文件则忽略）
- 配置文件用于补充后续的运行逻辑细节或者数据

#### 第三步：全局扫描
- 加载 `整体架构.md`，提取所有环节的【黄金指标】

#### 第四步：数据获取

- 找出所有环节的黄金指标
- 构建queryAndDrillDown的查询请求：
  - AbnormalDetail：由之前的分析结果中提取，如果没有则填null，不要随意编造
  - 构建MetricRequest
    - identifiers：即上述所有环节的黄金指标
    - queryStartTime：上述queryStartTime
    - queryEndTime：上述queryEndTime

#### 第五步：挑出有问题的环节

- 使用queryAndDrillDown工具分析黄金指标，找出有问题的黄金指标
  - 列出各个指标在 [abnormalStartTime, abnormalEndTime] 内的波动幅度
  - **指标验证(必须严格执行)**：指标必须在 `[abnormalStartTime, abnormalEndTime]` 内有吻合的波动时间点才算有问题的指标
  - 有问题的指标中rootCaseMaps作为有问题的维度，作为补充的细节信息
- 若某环节黄金指标异常则该环节标记为有问题
- **tag 维度下钻（标记异常后执行）**：对每个已判定异常的 **identifier**，调用 **`findMetricCoreByIdentifier`** 读取 MetricsCore；据合法 tag 选定 **`groupBys`**；在同一 **`[abnormalStartTime, abnormalEndTime]`**、同一 entity（及若有则同一 AbnormalDetail）下再次 **`queryAndDrillDown`**（传入 **`groupBys`**，依据 **`rootCaseMaps`** 归纳主导异常的维度取值并写入结论）
- 异常指标下的rootCaseMaps
  - 如果是null代表当前指标的问题并不集中在某几个tag维度上而是所有维度都有这种问题
  - 如果不是null代表当前指标的问题集中在rootCaseMaps对应的维度上
- **执行闸门（硬约束）**：凡是已标记异常的 **identifier**，若未完成上述 tag 下钻（未成功获取 MetricsCore、未形成有效 `groupBys`、或未执行带 `groupBys` 的二次 `queryAndDrillDown`）则本次分析无效，禁止进入结论推演与最终结论输出

#### 第六步：环节的详细分析

- 对有问题的环节，加载对应的 `整体逻辑.md`，提取出该环节的非黄金指标
- 按照第四步的方式构建查询请求，来查询非黄金指标以及进行下钻
  - **tag 维度下钻（标记异常后执行）**：对每个已判定异常的 **identifier**，调用 **`findMetricCoreByIdentifier`** 读取 MetricsCore；据合法 tag 选定 **`groupBys`**；在同一 **`[abnormalStartTime, abnormalEndTime]`**、同一 entity（及若有则同一 AbnormalDetail）下再次 **`queryAndDrillDown`**（传入 **`groupBys`**，依据 **`rootCaseMaps`** 归纳主导异常的维度取值并写入结论）
- **多级下钻逻辑**：
  - 若涉及子环节（如内存管理 -> 内存回收），必须先获取子环节指标再推导。
  - **因果链条建立**：必须描述“因为指标 A 突变导致了指标 B 的异常”，严禁孤立看待指标。
- **最终验证(必须严格执行)**：所有推导出的原因，其对应指标必须在 `[abnormalStartTime, abnormalEndTime]` 内有吻合的波动时间点。

#### 第七步：结论推演

- 仅基于已识别的异常指标，推理 1～3 条因果链条
- 每条链条需包含：根因指标 →（可选）中间指标 → 结果指标
- 根因判定：根因指标必须在时间窗内发生突变
- 若黄金指标在时间窗内均无突变：直接输出未发现异常，禁止假设根因
- 因果校验（必须全部满足）：机制合理、时间顺序正确、符合 Redis 架构、无更合理替代解释
- 量级门槛：若候选原因 `A` 的变化量显著小于结果 `B`（默认阈值：`delta(A) < delta(B) / 5`），`A` 不得作为根因，只能降级为促发因素或伴随现象
- 反向因果检验：必须同时对比 `A -> B` 与 `B -> A`；若后者在时间顺序、机制合理性、量级解释力上更强，则禁止输出 `A -> B` 为根因
- 案例：`connections_received` 约 `11 -> 25`（约 `+2.27x`），但 `cpu_cfs_throttled_seconds` 约 `+207x`；量级不闭合时优先判定 `CPU CFS throttling -> 事件循环受压 -> 吞吐下降/连接堆积`
- **反直觉校验（硬约束）**：当出现“吞吐/命令下降 + Redis 组件自身 CPU 下降”组合时，**不得**直接判定为“外部请求减少”；必须并列考虑“资源层限流/抢占/run queue 堵塞导致拿不到 CPU”，并进入第八步交由 `schedule` 决策下钻验证。
- 输出约束：最终仅允许一个结论，禁止多根因、模糊或猜测性结论

### 第八步：决策是否下钻到资源层(k8s/docker/process)

**host**和**node**是同一个概念，根据实际情况进行选择，下面统一叫**host**
**决策优先级（硬约束）**：先判断是否属于性能恶化场景；若是，则必须下钻资源层，禁止直接收敛。
**路径约束（硬约束）**：第八步下钻到 `host` 层时遵循双条件约束：组件层禁止直接下钻 `host`；资源层（`k8s`/`docker`/`process`）允许直接下钻 `host`（通常由 `schedule` 决策）。
**反直觉校验（硬约束）**：当出现“组件 CPU 下降 + 吞吐/命令下降”组合时，**不得**直接收敛为“外部请求减少”；必须并列评估资源层限流、CPU 抢占、run queue 堵塞等可能，并交由 `schedule` 继续资源层下钻验证。

如果判断**可能是资源层问题导致的性能恶化**，则：
- 交由 `schedule` skill 决策并继续深入资源层分析
- **性能出现恶化的场景**必须交由 `schedule` skill 决策并继续深入资源层分析，因为很可能是资源层恶化导致当前组件运行恶化
- **慢查询（slowlog/latency 异常）默认归为性能恶化场景**，必须交由 `schedule` 继续下钻资源层

如果已经找到**明确的组件级根因**，且与资源层无关，则：
- **不需要下钻**
- 直接输出最终结论和优化建议
