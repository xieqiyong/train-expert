## 核心运行说明

本文件用于对选定版本的 `{项目名}` 进行故障定位。

在执行本文件前，必须先由根 `SKILL.md` 确定版本目录。以下所有文档路径、架构知识和 `static_package/` 的读取范围，都默认相对于该版本目录。

### 运行流程

**九步法则**
- **必须强制执行**
- **开始、中间、结束必须记录已分析的步骤、未分析的步骤**

#### 第一步：明确查询时间
- 如果已经有queryStartTime、queryEndTime，则使用 queryStartTime、queryEndTime
- 如果没有，调用工具 `getCurrentTimeRangeMillis` 方法获取当前查询时间范围，工具参数timeRangeMillis是查询范围的毫秒值，推荐600000

#### 第二步：加载配置
- 调用 shuku skill 加载当前项目的配置文件（如果配置文件为空则代表没有采集对应的配置文件则忽略）

#### 第三步：全局扫描
- 加载 `整体架构.md`，提取所有环节的【黄金指标】

#### 第四步：数据获取

- 调用 shuku skill 一次性查询上述所有环节的黄金指标
- 构建查询请求：
  - AbnormalDetail：由之前的分析结果中提取，如果没有则填null，不要随意编造
  - 构建MetricRequest
    - identifiers：即上述所有环节的黄金指标
    - entityHost：从schedule中提取的实体的ip地址
    - entityPort：从schedule中提取的实体的端口号，如果没有则不用填写，不能按照常理编造（**必须严格执行**）
    - queryStartTime：上述queryStartTime
    - queryEndTime：上述queryEndTime

#### 第五步：挑出有问题的环节

- 使用queryAndDrillDown工具分析黄金指标，找出有问题的黄金指标
  - 列出各个指标在 [abnormalStartTime, abnormalEndTime] 内的波动幅度
  - **指标验证(必须严格执行)**：指标必须在 `[abnormalStartTime, abnormalEndTime]` 内有吻合的波动时间点才算有问题的指标
  - 有问题的指标中rootCaseMaps作为有问题的维度，作为补充的细节信息
- 若某环节黄金指标异常则该环节标记为有问题

#### 第六步：环节的详细分析

- 对有问题的环节，加载对应的 `整体逻辑.md`，提取出该环节的非黄金指标
- 按照第四步的方式构建查询请求，来查询非黄金指标以及进行下钻
  - 有问题的指标中rootCaseMaps作为有问题的维度，作为补充的细节信息
- **多级下钻逻辑**：
  - 若涉及子环节，必须先获取子环节指标再推导
  - **因果链条建立**：必须描述“因为指标 A 突变导致了指标 B 的异常”，严禁孤立看待指标
- **最终验证(必须严格执行)**：所有推导出的原因，其对应指标必须在 `[abnormalStartTime, abnormalEndTime]` 内有吻合的波动时间点
- 若文档不足以支撑结论，则继续读取选定版本目录下的 `static_package/` 进行源码级补充分析

#### 第七步：组件cpu、memory、io、net等资源的分析

- 根据组件的host和port，调用detectEntity工具找到对应的资源层实体
- 调用对应的资源层skill对资源进行分析

#### 第八步：结论推演

##### 因果链条生成
- 仅基于已识别的异常指标，推理 1～3 条因果链条
- 每条链条需包含：根因指标 -> （可选）中间指标 -> 结果指标

##### 根因判定（硬约束）
- 根因指标必须在 `[abnormalStartTime, abnormalEndTime]` 内发生突变
- 突变需为数值级异常（突升 / 突降 / 结构性变化）
- 若黄金指标在该时间窗内均无突变：
  - **直接输出：`未发现异常`**
  - **禁止假设根因**

##### 结论推演
- 从最可能的因果链条开始
- 由因到果逐层验证下游指标是否符合预期

##### 因果校验（必须全部满足）
- 机制合理
- 时间顺序正确
- 符合系统架构
- 无更合理替代解释

##### 结论修正
- 任一校验失败 -> 放弃该链条，推演下一条
- 全部链条失败 -> 输出：`未发现异常`

##### 输出约束
- 最终仅允许一个结论
- 禁止多根因、模糊或猜测性结论
- 给出优化建议

### 第九步：决策是否下钻到宿主机

如果最终根因是资源层的问题，则需要继续下钻到宿主机继续进行资源分析。

如果已经找到**明确的组件级根因**，且与资源层无关，则：
- **不需要下钻**
- 直接输出最终结论和优化建议

### 一次性输出要求

- 明确要求 LLM 在获取数据后，在内部完成所有逻辑推理
- 严禁输出"准备进入下一步"等过渡性语言
- 一次性输出完整分析结果

### 重要约束

1. **严格遵循SOP**：所有的排查必须以.md文档为标准作业程序
2. **禁止跳跃**：在Skill路径未走完前，不得直接给出基于通用经验的结论
3. **精准权衡**：
   - 若Skill逻辑命中：直接给出Skill中的优化建议，并引用文档原文
   - 若Skill逻辑未命中：先说明"已排查完私有知识库，未发现匹配项"，再补充通用知识
4. **逐行对照**：分析时逐行对照md中的逻辑说明，不进行脑补
5. **时间展示**：不能是一个数值，需要调用 `formatTime(时间戳数值)` 工具；如果时间戳转换已经出现过则直接复用，不要频繁重复调用工具

## 架构知识

本文件依赖以下知识文档：

- `整体架构.md`：项目整体架构说明及黄金指标定义
- `环节目录/整体逻辑.md`：环节的整体逻辑说明
- `环节目录/逻辑细节.md`：子环节或关键逻辑的详细说明
- `static_package/`：当文档无法支撑结论时，用于补充读取的源码或原始材料
